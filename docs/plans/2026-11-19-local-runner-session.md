# Local runner session implementation plan

> For Hermes: implement and independently review the bounded native session vertical before publication.

Goal: current owner explicitly authorizes one immutable user-managed session for an agent public key; the enrolled runner pulls it, creates its own Tailcat identity, hands back an ephemeral capability through the authenticated coordinator, runs native MCP, and proves cleanup. No billing or paid provider I/O.

Architecture: reuse IdentityAuthority and local_runners. A separate per-session execution capability (not account:read) permits only that session's address/status and cancellation. PostgreSQL owns admission and narrow transitions; one active session per runner, immutable generation 1, no automatic retries/reassignment. Local absolute expiry ends the runtime even during coordinator outages. New intent after cleanup gets a new session ID; this avoids a second retry scheduler beside Temporal. Coordinator address custody is volatile process memory only; loss requires the same runner to republish, never relaunch elsewhere. This first coordinator composition is single-process, not HA.

Files/tests: add runner_sessions.py + migration 0009, runner_transport.py, local_session_runner.py and real PostgreSQL/session/native acceptance tests. Mount additive routes in api.py. Keep Blender bootstrap/tool invocation only in opt-in product acceptance, not Core runtime code.

Sequence:
1. Fix #25 using a hard subprocess exchange deadline plus existing bounded HTTP framing; prove real slow headers/body termination and cleanup before execution reuse.
2. Owner session admission, session-specific token, immutable public key/image/resource/TTL, existing runner authentication. Real PostgreSQL tests for read-only agent denial, changed-input replay, concurrent admission, revoked/expired authority, generation and illegal transitions.
3. Outbound assignment poll, ready-address republish and stopped receipt. No raw capability address or private key in database/logs. Polling does not renew absolute TTL. Cancellation/expiry changes desired state; terminal success requires deletion acknowledgement.
4. Local runner Tailcat key generation in ephemeral private runner storage; fixed allowlisted agent; fixed trusted local workload command; immutable Docker image/resource bounds, no workload socket mount or public management API. Deterministic owned container name, bounded subprocesses and explicit final removal/readback.
5. Native opt-in acceptance: use published bpy image digest, agent-owned key, coordinator admission -> authenticated runner poll -> address -> MCP initialize/tools/list/version -> stop and expiry. Verify all owned children/container/private directories removed, negative agent identity and account controls; retain sanitized wire/version evidence. Return exact candidate for review before push.

Commercial direction (accepted, not implemented): reusable Fstack Cloud private prepaid credit accounting with Stripe initially for payments, replaceable billing adapters, Lago optional advanced integration later. Preserve shipped Lago hooks; do not remove or replace them in this slice. Each business keeps isolated identities/accounts/balances/data while sharing code. Product-neutral balance/reserved/spendable, quotes, offers and usage are future HTTP/MCP contracts; product adapters own performance estimates and decomposition. Credit denomination/rates, payments and charges are not authorized. Next small private credit step is to specify immutable reservation identity and atomic concurrent reserve/settle/release against existing account bindings, then prove real-PG overspend controls without payment I/O; Stripe itself is not the reservation authority.

## Next private accounting acceptance — design/review queue only

- Managed execution is prepaid-only. Preserve separate purchased balance, reserved holds and spendable balance. Atomically reserve an approved maximum across concurrent jobs before dispatch; no overdraft. Settle actual metered usage at the accepted immutable rate/conversion version, not the initial estimate. Release unused holds back to spendable balance; purchased unused funds stay in the wallet, with no automatic refund.
- Credit purchases and job spend authorization are distinct. Optional auto-top-up requires explicit customer consent to threshold/amount/currency, versioned mandate and per-transaction/period limits. Agents cannot enlarge a card mandate. Standing approval may cover top-ups only within those limits; changed job scope/estimate requires incremental job-budget approval.
- Only verified successful payment can issue credits, once logically. Declines, authentication-required responses, pending payments, timeouts and delayed webhooks create no spendable balance. Use immutable purchase identity, single-flight top-up and idempotent webhook/payment reconciliation across concurrent jobs; recheck mandate revocation. Preserve existing identity/account bindings, provider fences and native payment hooks where applicable; do not infer that existing Lago integration already implements these credit reservations.
- Reserve conservative checkpoint/shutdown/deletion tail before launch, including pending allocations/offers and applicable provider minimums. Low-water controls consider current burn rate, payment latency and measured shutdown latency. Freeze new work and warn the agent before the limit; require approved replenishment or incremental approval. At the safe cutoff checkpoint, pause where actually supported, or stop/delete and verify absence. Never continue on the assumption that payment will succeed.
- A local hard TTL/expiring allocation budget lease must bound managed execution when the agent or coordinator is offline. This local user-managed slice's absolute TTL is not yet a financial budget lease. Provider lag, minimum charges, unexpected shutdown failure, crashes and chargebacks can still create liability: do not promise mathematically zero infrastructure exposure.
- Required real-PostgreSQL/private-fixture gates before enablement: concurrent overspend denial; duplicate/lost reserve and settle acknowledgements; actual-use settlement plus unused-hold release; successful-payment-only credit issuance; decline/authentication-required/timeout paths; simultaneous top-up triggers and duplicate/out-of-order/delayed webhooks; mandate revocation and cap enforcement; estimate growth requiring approval; low-water warning/new-work freeze; offline cutoff and delayed-delete liability reconciliation. No live payment or credits issuance is authorized by this plan. Pack denominations and credit-to-currency conversion remain unspecified.
